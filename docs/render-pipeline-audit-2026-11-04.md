# Аудит процесса монтажа и рендера

4 ноября 2026 года. Основа сравнения — `0ca3778`.

Убраны повторные вычисления и ненужный второй экспорт. Сохранены единый пакет
Telegram Motion Style, база 50 источников, камера V4, материал жестов и текстовые
эффекты «Обычный» и «Эмоциональный».

## Исправления

| Найденная работа | Изменение | Граница |
| --- | --- | --- |
| `prepare --render-base` всегда запускал полный рендер | Совпавшая база переиспользуется; `--force-base` оставлен для принудительного пересчёта | Входы по-прежнему хешируются; геометрия/частота/число кадров базы проверяются |
| Кеш не учитывал изменения движка | В подпись включены исходники базового движка и версии Pillow/NumPy | После обновления FFmpeg использовать `--force-base` |
| Запись целиком сканировалась в `render.py`, затем ещё раз в `compose.py` | При явных offset/end второй вызов читает только размеры | Полная проверка входных PTS в `render.py` сохранена; старый автоматический sync сохраняет свой анализ |
| Декодеру заказывалась дополнительная секунда за концом вывода | Декодируется запланированная длительность | Отсутствующий финал остаётся ошибкой; клонирование кадров не добавлено |
| При видеофоне создавался неиспользуемый градиент | Статичный фон создаётся только когда используется | Сами фоновые кадры и их часы не менялись |
| Поиск экрана в рамке перебирал миллионы пикселей Python-кодом Pillow | Компонент прозрачности заполняется горизонтальными участками через NumPy | Сохранены порог alpha и связность; новых зависимостей нет |
| Repair-подложка масштабировалась на каждом активном кадре | Неизменный размер рассчитывается при загрузке слоя | Масштабируемый объект и его движение рассчитываются как раньше |
| Невалидный звук обнаруживался после видеорендера | Проверка звука перенесена перед дорогим проходом | Ошибка останавливает работу до рендера |
| Пустой редакционный план экспортировался через браузер и H.264 второй раз | Экспорт без `text`/`audio` копирует готовую базу | Планы с дорожками по-прежнему используют Remotion; существующий выход не перезаписывается |

Изменение текста/звука не сбрасывает базу. Изменение записи, рамки, камеры,
объектных слоёв или кода движка сбрасывает её. Старые подписи кеша потребуют
одного нового рендера после обновления.

## Измерения

Локальный калиброванный фрагмент Kino: исходник 1260×2736, выход 1920×1920,
60 fps, 1,5 с / 90 кадров, рамка, один тап, видеофон. Одинаковые параметры:
`--scale 3 --offset 0 --start 0 --end 1.5 --size 1920x1920 --fps 60
--camera none --ring telegram --tap-profile reference --static-background
--no-shadow` и один и тот же видеофон. Исходные медиа не входят в репозиторий.

Без профилировщика, порядок запусков: до → после → после → до.

| Версия | Запуски, с | Медиана, с |
| --- | --- | --- |
| До | 26,740; 24,987 | 25,863 |
| После | 12,336; 11,842 | 12,089 |

На этом фрагменте время сократилось примерно на 53%, скорость выросла в 2,14 раза.
Это два замера каждой версии на рабочем Mac, без изоляции фоновой нагрузки.
Выигрыш нельзя переносить на весь монтаж или длинные ролики: часть экономии
приходится на однократную подготовку рамки и сканирование входа.

Дополнительный cProfile показал прежние затраты на `ImageDraw.floodfill`
и покадровый `ffprobe`; его времена не используются в таблице выше.
В новой версии наибольшая оставшаяся статья — масштабирование изображения
телефона на каждом кадре.

Повторный `prepare --render-base` синтетической сцены занял 0,263 с;
SHA-256 базы и её mtime сохранились. Экспорт этой базы без редакционных дорожек
занял 0,074 с, копия совпала побайтно. Эти замеры относятся к маленькой сцене
480×480, 240 кадров; это проверка пропуска работы, а не оценка скорости 4K.

## Проверки

- 39 Python-тестов, включая интеграции с FFmpeg, без пропусков.
- 11 Node-тестов, включая существующее сравнение Swift/JS для текста.
- Для исходной и новой версии проверочного фрагмента совпали все 90
  декодированных кадров (`framemd5`), включая тап на видеофоне.
- Быстрая маска рамки совпала с прежним Pillow floodfill на 32 масках:
  случайных, с отверстиями, узкими проходами и внешней прозрачностью.
- Подтверждены повторное использование базы, сброс при изменении записи/движка,
  принудительный пересчёт и ранний отказ при ошибке аудио.
- Экспорт без Remotion-зависимостей прошёл; повторный экспорт сохранил имеющийся файл.
- Создан новый рабочий проект. Полный синтетический экспорт с обоими текстовыми
  эффектами и звуком: 480×480, 60 fps, 240 кадров, AAC; полное декодирование
  с `ffmpeg -xerror` прошло.
- Метаданные навыка и локальные Markdown-ссылки проверены.

Эти проверки подтверждают механику рендера. Новый пользовательский ролик
не снимался; приложение, симуляторы и установленные навыки не изменялись.
Художественное качество старого ролика и правильность каждого его клика
не объявляются исправленными этим рефакторингом.

## Изменения порядка работы

В чатах «Исправить анимацию ролика» и «Найти репозитории для монтажа видео»
повторялись замечания к рывкам, темпу ввода, переносу кнопки за границу,
длинным паузам и отсутствующему видимому результату. Отдельно владелец просил
собирать дефекты вместе, а не выдавать очередной экспорт после каждого исправления.
В чате «Обогати Telegram-Style-Motion» уточнены единый пакет и названия эффектов.

В основной процесс добавлены выбор одного подходящего движка, различение
ошибки исходника и композиции, совместный список исправлений до полного экспорта
и короткий предпросмотр изменённого движения. Метаданные читаются без полного
декодирования; для целостности достаточно одного прохода с проверкой ошибок.
Повтор проверок зависит от изменения файла или нерешённого дефекта.

Пример фокусирования теперь увеличивает объект на месте (`offset: [0, 0]`).
Перенос за рамку остаётся осознанным отдельным приёмом. В инструкции отмечена
ранее установленная проблема PTS/DTS в отдельных записях Simulator;
`+igndts` не превращён в универсальный флаг для всех источников.

## Следующие улучшения

1. Для добавления одного только звука реализовать FFmpeg-mux с `-c:v copy`.
   Сейчас такие планы всё ещё проходят через Remotion и повторное кодирование.
2. Оптимизировать проекцию телефона на основе профиля. Отдельная подготовка
   неподвижных частей может помочь, но потребует проверки пикселей, масок,
   обрезки и матового кольца; в этом изменении алгоритм масштабирования сохранён.
3. При следующих роликах отдельно измерять захват, нормализацию, базовый рендер,
   редакционный экспорт и проверки. Это позволит увидеть, где фактически ушло
   время, прежде чем добавлять новый движок или ещё один адаптер.
